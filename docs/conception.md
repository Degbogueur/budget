# Budget Step by Step: Design

Design document for the budget app. It fixes the scope, the domain model, the API contract and the screens before any code is written.

> The API contract is the boundary between back end and front end. As long as it does not change, each side can evolve on its own.

## 1. User stories

Only what fits in one day is kept.

| #   | As a user, I want to...                                   | So that...                          |
| --- | --------------------------------------------------------- | ----------------------------------- |
| US1 | create an account and sign in                             | my expenses stay private            |
| US2 | add an expense (description, amount, category, date)      | I can track where my money goes     |
| US3 | see the expenses of a month, filterable by category       | I can find an expense               |
| US4 | see the monthly total and the breakdown by category       | I know where I spend the most       |
| US5 | delete an expense                                         | I can fix a data entry mistake      |
| US6 | create my own category                                    | I can classify an expense my way    |

US6 applies when none of the built-in categories fits.

## 2. Domain model

Two entities, each enforcing its own invariants.

### Expense

| Field         | Type       | Rule                                                                 |
| ------------- | ---------- | -------------------------------------------------------------------- |
| `Id`          | `int`      | Generated by the database                                            |
| `UserId`      | `string`   | The owner. A user never sees other users' expenses                   |
| `Description` | `string`   | 2 to 100 characters, trimmed                                         |
| `Amount`      | `decimal`  | Greater than 0, at most 100,000, at most 2 decimal places            |
| `CategoryId`  | `int`      | A category visible to the owner (built-in, or created by the owner)  |
| `Date`        | `DateOnly` | Not in the future                                                    |

### Category

| Field    | Type      | Rule                                                                                                                              |
| -------- | --------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `Id`     | `int`     | Generated by the database                                                                                                         |
| `UserId` | `string?` | `null` for the six built-in categories (Food, Housing, Transport, Leisure, Health, Other), otherwise the user who created it       |
| `Name`   | `string`  | 2 to 30 characters, trimmed. Unique per user, case-insensitive                                                                    |

A custom category is private: other users cannot see it or use it.

### Why put the rules in the entities?

Because it makes it impossible to create an invalid expense, whatever code creates it (an endpoint, an import, a test). This is the core idea of a rich domain model in DDD. The opposite, an entity with only public `get; set;` and rules scattered across controllers, is called an anemic model.

## 3. API contract

All routes are under `/api`. JSON is camelCase (ASP.NET Core default).

| Method | Route                                  | Body                                      | Response                          |
| ------ | -------------------------------------- | ----------------------------------------- | --------------------------------- |
| POST   | `/api/auth/register`                   | `{ email, password }`                     | 200 or 400                        |
| POST   | `/api/auth/login?useCookies=true`      | `{ email, password }`                     | 200 + cookie, or 401              |
| POST   | `/api/auth/logout`                     | none                                      | 204                               |
| GET    | `/api/auth/me`                         | none                                      | 200 `{ email }` or 401            |
| GET    | `/api/categories`                      | none                                      | 200 `[{ id, name, isCustom }]`    |
| POST   | `/api/categories`                      | `{ name }`                                | 201 or 400                        |
| GET    | `/api/expenses?month=2026-11&categoryId=4` | none                                  | 200 `[Expense]`                   |
| GET    | `/api/expenses/summary?month=2026-11`  | none                                      | 200 `{ month, total, count, byCategory }` |
| GET    | `/api/expenses/{id}`                   | none                                      | 200 or 404                        |
| POST   | `/api/expenses`                        | `{ description, amount, categoryId, date? }` | 201 or 400                     |
| PUT    | `/api/expenses/{id}`                   | same as POST                              | 204, 400 or 404                   |
| DELETE | `/api/expenses/{id}`                   | none                                      | 204 or 404                        |

### Business rule errors

A business rule violation always returns a `ValidationProblem` (RFC 9457):
```
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "amount": ["Amount must be greater than 0."]
  }
}
```
The keys of `errors` are property names. The front end uses them to display each message under the right field.

## 4. Architecture decisions

| Decision          | Choice                                                                          | Why                                                           |
| ----------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| API organization  | One project, with `Domain`, `Data`, `Features` and `ErrorHandling` folders      | Simple, readable, fast to write                               |
| Business logic    | In the `Expense` and `Category` entities                                        | A single source of truth for the rules                        |
| Data access       | `DbContext` used directly in endpoints, no repository                           | `DbContext` is already a unit of work and a set of repositories |
| Read / write      | Reads projected to DTOs with `AsNoTracking`; writes go through entity methods   | The spirit of CQRS without the ceremony (no MediatR)          |
| Database          | SQLite in dev and in production                                                 | Same behavior everywhere, no server, ideal for a 1 GB VM      |
| Authentication    | ASP.NET Core Identity with an HttpOnly cookie                                   | Nothing to store in JavaScript, the browser handles it        |
| Hosting           | The API also serves the React files                                             | A single origin: no CORS, simple cookie                       |
| Language          | Everything that is part of the app is in English                                | Professional convention; multilingual support comes later     |

## 5. Language

The application is written entirely in English:

- source code and comments
- user interface texts
- API error messages
- built-in category names (Food, Housing, Transport, Leisure, Health, Other)
- routes (for example `/login`)
- commit messages, following Conventional Commits (for example `feat: add expense creation endpoint`)

This is a professional convention. Multilingual support may be added later as a bonus step.
